# Drift Dashboard — Component Guide

A walkthrough of the actual UI, in the order it renders on screen, with the real component names, props, and
files. See `Product_README.md` for the data pipeline and concepts (drift severity, confounds, relatedness) that
feed everything described here.

## App-level flow

`src/pages/AppRoot.tsx` is the only router in the app — plain `useState`, no routing library. It reads the
current session from `useSessionStore` and decides which screen to show:

1. **`reopened` state set** (a comparison was reopened from local history or imported from a file) → renders
   `ComparisonView` directly with `precomputedComparison` set, `logFilesById` empty, and a fresh
   `EvidenceIndex`. This is the one path that skips recomputation entirely.
2. **No runs uploaded yet** → `UploadPanel`, with `onOpenRecent` (opens a history entry by id via
   `getRecentComparison`) and `onImportReport` (parses an uploaded `.driftreport.json` via `importReport`)
   wired in.
3. **Exactly one run** → `SingleRunView` for that run — there's nothing to compare yet.
4. **Two or more runs, viewing individually** (see step 6) → one `SingleRunView` per run, stacked.
5. **Two or more runs, relatedness not yet confirmed** → `RelatednessCheckView`, gating entry into the full
   comparison dashboard.
6. **Two or more runs, relatedness confirmed (or the user clicked past it)** → `ComparisonView`, the main
   dashboard.

`relatednessAssessment` is computed once, memoized, via `buildRelatednessAssessment(runs, logFilesById)`
whenever 2+ runs are present — it's threaded into both `RelatednessCheckView` and `ComparisonView`.

## UploadPanel

`src/components/UploadPanel.tsx`. The landing screen. A drag-and-drop zone (`#log-upload`, `accept=".jsonl"`,
`multiple`) accepts any number of `.jsonl` files; each is handed to `parseLogInWorker` in parallel
(`Promise.all`), and the resulting `BuiltRun[]` is appended to the session store via `addBuiltRuns` — one run
works as a single-run report, two or more unlocks comparison. A secondary "Import a previously exported report"
file input (`accept=".json"`) restores a `.driftreport.json` through `importReport`, bypassing parsing entirely
since that file already contains a fully-computed `Comparison`. Shows a `Spinner` while parsing and a plain
error message if any file fails. The right-hand column shows a static three-step "How it works" explainer plus
`RecentComparisonsList` when `onOpenRecent` is supplied.

## RelatednessCheckView

`src/pages/RelatednessCheckView.tsx`. Shown before the comparison dashboard whenever there are 2+ runs, so the
user can sanity-check that the uploaded logs actually describe the same task before trusting a drift comparison
built from them. Runs that clustered together as mutually `related` render as one grouped row (their shared
reasoning text shown once); every other pair renders as its own row, tagged with a `signal-badge` — `Related`
(neutral gray), `Review recommended` (amber, for `partial`), or `Unrelated` (red) — and the actual reasoning
sentence generated by `assessPairwiseRelatedness` (e.g. "same repository, different starting commit" or a
prompt-topic mismatch). A "Continue to comparison" button proceeds regardless of rating (relatedness is always
advisory, never blocking); a second "View runs individually instead" button appears only when
`assessment.hasAnyBelowFullConfidence`, routing to the per-run `SingleRunView` stack instead.

## ComparisonView — the main dashboard

`src/pages/ComparisonView.tsx`. Everything below renders in this exact top-to-bottom order.

### Header

- The app wordmark ("DRIFT") plus, as the page's `<h1>`, either the AI-suggested title (`aiTitle`, if
  `SuggestNamesButton` has produced one) or the deterministic `comparison.title` (the longest real prompt across
  all runs, title-cased — `generateComparisonTitle`).
- **`SuggestNamesButton`** (`src/components/SuggestNamesButton.tsx`), hidden when viewing a reopened report.
  Presentational only — its `loading`/`error` state and the actual Anthropic call live in `ComparisonView`
  itself via `runNaming()`, so the same generation logic backs both this manual button and the automatic
  first-load trigger (a `useEffect` keyed on the run-id set, gated on `isReopened` and on a key already being
  saved — it never auto-prompts for one). Clicking it either fires generation directly (a key is already
  available) or opens a small popover with an API-key entry form; a returned `error` also reopens that popover
  so the message is visible. A successful call replaces the header title and overlays `aiRunLabels` onto every
  run's display label throughout the rest of the page (`displayRuns`, a `useMemo` derived from `runs` — nothing
  about the underlying `Comparison` itself depends on these labels).
- Action buttons: **New comparison** (resets the session, only shown when `onNewComparison` is supplied),
  **Download PDF** (`window.print()` — the app's `theme.css` has a dedicated `@media print` block that flattens
  the dark theme to a light, ink-friendly one and hides interactive-only chrome), and **`ExportButton`**.

### RelatednessReminderBadge

`src/components/RelatednessReminderBadge.tsx`. Renders nothing when every pair is fully `related`. Otherwise, a
standing warning card listing each below-`related` pair's reasoning sentence, so the caveat stays visible while
scrolling the dashboard rather than only appearing once on the pre-comparison check screen.

### RunSummaryCards

`src/components/RunSummaryCards.tsx`. One card per run, color-coded via `runColor(index)`. Shows total prompt
character count (summed across every real prompt in the session, not just the effective last one — via
`extractPromptRecords`), working directory, turns, and tool calls (each an `AnimatedNumber`). Below the stats, a
collapsed `<details>` "View full prompt" reveals every real prompt the user sent in that session verbatim,
each timestamped, when there's more than one (e.g. an initial task description plus later follow-ups like
"start the server" or "/exit") — or a plain "No prompt captured for this run" if the log had none.

### Reopened-report notice

A plain status line ("Reopened from recent comparisons — evidence drill-down uses the already-computed values
only"), shown only when `precomputedComparison` was supplied. Reopened reports have no `LogFile` data available
(only the previously serialized `Comparison`), so several dashboard sections that need raw log access are
skipped entirely in this mode — see below.

### HeadlineKpiSection

`src/components/HeadlineKpiSection.tsx`. The row of large KPI cards — the dashboard's second visual row after
the run-summary cards. One card per key in `comparison.headlineMetricKeys` (up to 6, ranked by
`buildHeadline` — priority metrics like cost/tokens first, then by magnitude of deviation; approval-wait and
other-idle time are deliberately excluded from this automatic ranking even if they drifted, since they reflect
human response time rather than agent behavior). Each card shows the metric label, the two (or, for 3+ runs, the
range + outlier) values as `AnimatedNumber`s, and a `signal-badge` with the percent delta and severity label. A
card's left-border accent and background tint are driven by `SEVERITY_ACCENT_VAR`/`SEVERITY_BG_VAR`, both keyed
off the metric's `DriftSeverity` — see "Color system" below for the actual token values. If
`comparison.headlineMetricKeys` is empty, the section instead renders a single "No significant drift detected."
message.

### RecommendationsPanel — AI business insights

`src/components/RecommendationsPanel.tsx`, given `comparison`, `runs`, and `logFilesById`. Rendered for every
comparison, including reopened ones (unlike the charts and pairwise section below). Starts with a title/subtitle
and a "Generate business insights" button; clicking it either calls `generateBusinessInsights` directly (a key
is already saved) or opens an inline API-key entry form. Loading shows a `Spinner` ("Analyzing…"); a failure
shows a plain error line via `describeAnthropicError`.

Once insights arrive (`BusinessInsights` — `businessStats`, `dataQualityCaveats`, `recommendedAction`), the
panel renders, in order:

1. **Recommended action** — a single one-sentence "if you do only one thing" line.
2. **The business-stat card grid** (`business-stats-grid`, up to 4 cards, each a **`BusinessStatCard`**
   (`src/components/BusinessStatCard.tsx`) — the richest component in the dashboard. Anatomy of one card:
   - Header: a plain category pill (cost / time / efficiency / tool_usage / quality / workload / data_quality /
     other) and an impact pill (high / medium / low / informational, color-coded — see below), above a
     short business-facing title.
   - The figure: the first two of the stat's per-run values, large and prominent, joined by a `→` arrow (e.g.
     `$3.25 → $12.83`); any additional runs beyond the first two list below as `Run: value` pairs. Under that,
     a short bold comparison string (`"3.9x"`, `"+42%"`, or, for a duration/ratio metric, `"21.4 min vs 1.7
     min"`) and the metric's plain-language label. **Every one of these numbers is precomputed in code**
     (`buildBusinessInsightsPayload.ts` / `formatBusinessValue.ts`) — the AI only ever selects which candidate
     metric to feature and writes the surrounding prose; it cannot alter or invent the figure itself.
   - Explanation (what the numbers mean) and a separately-labeled "Why it matters" business implication.
   - An optional recommendation line (only rendered when the model actually gave one, with a check-circle icon).
   - A metadata footer: the source metric key (`stat.metricKey`, in `<code>`) and a plain confidence label.
   - An optional caveat line (warning-colored) when a confound or data-quality issue qualifies the finding.
3. **Data-quality caveats** — a plain bulleted list (only rendered when non-empty) tying each run's data-quality
   issue (e.g. a resent prompt) to which business metrics it taints.

If the model returns zero business stats, the panel shows "Nothing in this comparison warranted a business
insight" instead of an empty grid.

### Comparison charts

`src/components/CacheIntensityChart.tsx`, `ToolUsageChart.tsx`, `OverheadTrendChart.tsx`,
`DurationBreakdownChart.tsx`, in a 2-column grid. **Hidden entirely for reopened reports** (they need raw
per-event `LogFile` data to compute from, which a reopened report doesn't have). All four share the same
run-count-driven layout strategy, computed independently in each component (not a shared prop):

- **≤ 4 runs**: grouped horizontal bars (`HorizontalBarRows`), one color-coded bar per run per sub-metric.
- **5–8 runs**: for `CacheIntensityChart` specifically, a compact strip plot (one dot per run on a shared axis)
  instead of bars, to stay legible; the other three charts keep their own layout down to the 8-run boundary.
- **> 8 runs**: every chart falls back to `DistributionChart` — a box-plot-style aggregate view (median line,
  interquartile box, labeled outlier dots) per sub-metric, since per-run color coding stops being legible past
  that point.

What each shows:
- **CacheIntensityChart** — fresh-context tokens created per Read call, per Edit call, and per tool call overall
  (the "how much redundant context is this run re-injecting" question).
- **ToolUsageChart** — executed tool-call counts grouped by tool name, one group per tool actually used by any
  run in the comparison.
- **OverheadTrendChart** — the one `recharts` line chart: `cache_read_tokens ÷ output_tokens` across each
  session's quartiles, showing whether overhead grows across a session. Only the endpoint of each line gets a
  visible dot with its value printed beside it, to stay readable; beyond 6 runs every line except the highest-
  and lowest-growth run fades to reduce clutter, and the footnote line below the chart prints each run's overall
  growth multiple.
- **DurationBreakdownChart** — for ≤ 8 runs, stacked horizontal bars per run showing active / approval-wait /
  other-idle time as a percentage of that run's total wall-clock duration.

### Full comparison table

`src/components/ComparisonTable.tsx`, wrapped in a `#full-comparison-table` card (the headline section's
"view full table" affordance scrolls here). Columns, in order: **Metric** (a button that expands/collapses an
evidence row below it), one column per run (color-coded, `not-available` cells shown as muted text instead of a
raw dash), **Signal** (a `SignalBadge` for the metric's drift severity, plus a small confound-flag chip when
`overriddenByConfound` is set, its `title` attribute carrying the confound's full description), and, only when
`onPinMetric`/`onUnpinMetric` are both supplied, a **Pin** column. The table used to also show Min / Median /
Max / Spread / Outlier columns; those were removed — that group-statistics information still surfaces on the
`HeadlineKpiSection` cards for N-run comparisons (as a "Range: min–max" line plus outlier callout) instead of
duplicating it here.

- **`PinMetricToggle`** (`src/components/PinMetricToggle.tsx`): a star icon toggling `pinMetric`/`unpinMetric`
  in the session store. A pinned metric is guaranteed a spot in the headline section regardless of its
  classified severity.
- **Clicking a metric's name** expands an inline row containing **`EvidenceDrilldownPanel`**
  (`src/components/EvidenceDrilldownPanel.tsx`): every raw log event backing that metric's value, resolved via
  `EvidenceIndex.resolve()` against `findEvidenceForMetric` references (tool-usage metrics point at the matching
  `tool_decision` events; duration metrics point at the run's first/last event; everything else points at every
  main-task `api_call`). For a reopened report — no `LogFile` data available — this instead shows "Original log
  file not available — showing already-computed values only."

The same `ComparisonTable` component is reused a second time for the pairwise sub-view (see below), with the
`pinnedMetricKeys`/`onPinMetric`/`onUnpinMetric` props omitted there, so that instance never shows a Pin column.

### SignalLegend

`src/components/SignalLegend.tsx`. A small footer strip: one colored dot per run (via `runColor`) plus three
severity swatches — large/categorical drift (red), moderate drift (amber), and no-drift/uninterpretable (gray).

### Pairwise comparison

Rendered only when `!isReopened && runs.length > 2`. **`PairwiseSelector`**
(`src/components/PairwiseSelector.tsx`) — two plain `<select>`s, "Run A" and "Run B" — lets the user pick any two
of the loaded runs; picking the same run in both slots swaps the two selections instead of allowing a duplicate.
The selected pair is passed through `buildComparison` again (a fresh, independent two-run `Comparison`, not a
filtered view of the N-run one) and rendered in a second `ComparisonTable` instance below the selector.

## SingleRunView

`src/pages/SingleRunView.tsx`. Used whenever there's exactly one run to look at — either only one file was
uploaded, or the user chose "View runs individually instead" from the relatedness check (rendered once per run
in that case). If the run has no completed task activity at all, renders `EmptyRunState` and stops there.
Otherwise: an `UnrecognizedEventsNotice` (only if the log contained any events outside the known schema — never
silently dropped, always surfaced), a `SessionSummaryPanel` showing a plain, non-comparative one-line summary of
that run's own numbers (`composeSessionSummary` — no "vs.", no drift language, no reference to any other run),
and a plain metrics table listing every computed `RunMetricValue` for that run (label, value, and its
denominator description where one applies, e.g. "per turn (83)").

## Supporting and shared components

- **`SignalBadge`** (`src/components/SignalBadge.tsx`) — the small colored severity pill, reused by
  `ComparisonTable` and `RelatednessCheckView`; a thin wrapper mapping `DriftSeverity` to a CSS class.
- **`AnimatedNumber`** (`src/components/AnimatedNumber.tsx`) — every prominent numeric display in the dashboard
  goes through this: on mount (after an optional stagger `delay`), digit characters scramble through random
  values and progressively lock in left-to-right before settling on the real, already-formatted text.
  Punctuation (commas, decimals, the `—` placeholder) is left untouched. Respects
  `prefers-reduced-motion` (skips straight to the final value) and degrades gracefully in `jsdom` test
  environments where `matchMedia` doesn't exist.
- **`Spinner`** (`src/components/Spinner.tsx`) — a lightweight rotating SVG used for every genuine loading state
  ("Parsing…", "Analyzing…", "Naming…").
- **`Icon`** (`src/components/Icon.tsx`) — a single inline-SVG icon component with a fixed name union: `upload`,
  `download`, `warning`, `star-filled`/`star-outline`, `chevron-down`, `plus`, `external`, `history`,
  `check-circle`, `sparkle`, `key`, `close`, `shield`, `file-text`, `activity`.
- **`HorizontalBarRows`** (`src/components/HorizontalBarRows.tsx`) — the shared grouped-bar renderer behind
  `CacheIntensityChart` and `ToolUsageChart`'s ≤4-run layout.
- **`DistributionChart`** (`src/components/DistributionChart.tsx`) — the shared aggregate/box-plot fallback used
  by all four charts once run count exceeds 8.
- **`DataQualityNoteBadge`** and **`RejectedCallBadge`** (`src/components/`) exist in the codebase (rendering a
  single `DataQualityNote` or a rejected `ToolCallOutcome` respectively) but are not currently imported by any
  page — the data they'd present is instead surfaced inline elsewhere (the AI insights panel's data-quality
  caveats, and the comparison table's confound-flag chip).

## The color system

Two independent color dimensions, both defined as CSS custom properties in `src/styles/theme.css`:

**Per-run color** (`src/ui/runColors.ts`, `runColor(index)`), cycling through `--run-a` (`#e8871e`, orange),
`--run-b` (`#2fb8c4`, teal), `--run-c` (`#a78bfa`, purple), `--run-d` (`#f472b6`, pink), `--run-e` (`#84cc16`,
lime) — used for run-summary card accents, value text, chart bars/lines/dots, and the legend dots.

**Drift-severity color** (`DriftSeverity` → CSS token), used by `SignalBadge`, the comparison table's row tint,
`HeadlineKpiSection`'s card accent/background, and the legend swatches:

| Severity | Token | Color |
|---|---|---|
| `large` / `categorical` | `--signal-large` | red `#f0555a` (categorical additionally gets its own pink, `--signal-categorical` `#ec4899`, in the table's Signal badge) |
| `moderate` | `--signal-warning` | amber `#e0ad52` |
| `no-drift` | `--signal-neutral` | gray `#7c8494` |
| `cannot-determine` | `--signal-cannot-determine` | blue `#4f8bf0` |
| `uninterpretable` | `--signal-uninterpretable` | purple `#9b7ff0` |

`moderate` was previously mapped to `--signal-moderate` (green, `#10b981`) — changed to amber because green
reads as "fine/no issue" for something the dashboard is specifically trying to flag as a real, worth-noticing
drift. `--signal-moderate` itself still exists and is reused, unrelated to drift severity, for the "low impact"
tier on AI `BusinessStatCard`s (a different concept: how much a business finding matters, not how large a
metric's deviation is).

## Export and reopen

**`ExportButton`** (`src/components/ExportButton.tsx`) calls `exportReport(comparison, runs)`
(`src/reporting/exportReport.ts`), which serializes the current `Comparison` via `serializeComparison`
(`src/reporting/reportSerializer.ts`) — deliberately excluding raw `LogFile.events` and full prompt text, per
the same privacy boundary the local history uses — and triggers a browser download named
`<sanitized-title>.driftreport.json`. `UploadPanel`'s "Import a previously exported report" input reverses this
via `importReport`/`deserializeComparison`, reconstructing a `Comparison` and a set of `Run` stubs (with an
empty `taskPromptText`, since the real prompt text was never included in the export) that `AppRoot` feeds
straight into `ComparisonView` as `precomputedComparison`.

**`RecentComparisonsList`** (`src/components/RecentComparisonsList.tsx`), shown on the upload screen, lists every
comparison automatically saved to the local IndexedDB history (title, run labels, timestamp) and calls
`onOpenRecent(id)` on click, which `AppRoot` resolves via `getRecentComparison` — the exact same
serialize/deserialize round-trip as file export/import, just persisted locally instead of downloaded.

## State management

Two separate stores, deliberately not unified:

- **`useSessionStore`** (Zustand, `src/state/sessionStore.ts`) — in-memory only, cleared on refresh or "New
  comparison." Holds the currently uploaded `logFiles`/`runs`, the shared `EvidenceIndex` used for drill-down,
  and `pinnedMetricKeys`. `ComparisonView` reads `pinnedMetricKeys` and the `pinMetric`/`unpinMetric` actions
  directly from here and threads them into `HeadlineKpiSection` (which metrics qualify) and `ComparisonTable`
  (the Pin column).
- **`localHistoryStore`** (IndexedDB via `idb`, `src/state/localHistoryStore.ts`) — persists across sessions.
  `ComparisonView` writes to it once per freshly-built (non-reopened) comparison via a `useEffect` guarded by a
  ref (so React StrictMode's dev-only double-invoke doesn't write a duplicate entry). `UploadPanel` /
  `RecentComparisonsList` read from it to populate the "Recent comparisons" list and to reopen a past entry.
